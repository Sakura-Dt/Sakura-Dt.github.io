# TASK 01 · Scroll Storyboard / OPEN DRAFT

状态：**待审查的方案**。下面的尺寸、进度和运动参数均是原创设计目标，尚未实现、实测或性能验收。基于推荐方向A；如改选B/C，本文件需重写。文字ID对应 [copy-system.md](./copy-system.md)。

## 先明确动画的控制权

| 模式 | 进度由什么决定 | 向上滚动 | 本站用途 |
| --- | --- | --- | --- |
| Scroll-triggered | 进入视口启动一个按时间播放的动画 | 不会自然回到中间态，除非另写重播 | 很少量按钮/非关键注释提示 |
| Scroll-driven / scrub | 在起点s0与终点s1之间的滚动距离 | 按同一函数回退 | 标题对齐、框展开、预览流程、结尾开口 |
| Pin / sticky | 只规定一段距离内舞台的位置 | 位置遵循原生滚动 | 为两个需要对照的构图提供短暂稳定视野；不是一种动画进度 |
| 普通滚动 | 内容正常经过视口 | 原路返回 | 大部分个人介绍、项目说明、计划、学习记录、联系方式 |

局部场景进度定义为 `p = clamp((scrollY - s0) / (s1 - s0), 0, 1)`。动画状态是p的函数，不是“先等800ms再出现下一句”。用户停在35%，画面就停在35%；反向到20%，图形回到20%。滚动快速跨过场景时直接得到正确结束态，不依赖onEnter依次执行。

[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll-driven_animations/Timelines) 解释 scroll/view 时间轴与滚动的直接关联；[GSAP ScrollTrigger](https://gsap.com/docs/v3/Plugins/ScrollTrigger/) 区分 scrub、pin，以及数值scrub的追赶时间。本方案优先 `scrub: true` 保持直接映射，先不加惯性追赶或snap。缓动仅用于段内图形的位移分配，不让整条时间轴拖尾。

## 总体节奏与预算

六场，两个短pin。每一场都要改变叙事焦点，不是让六个相同卡片先后变亮。

| 场景 | 内容任务 | 桌面 | 手机 | 额外滚动距离 |
| --- | --- | --- | --- | --- |
| S01 先写一版 | 姓名、身份、主题与直接入口 | 短pin＋scrub | 普通滚动＋局部scrub | 桌面0.70V；手机0 |
| S02 从这里开始 | 教育、语言基础与关注方向 | 普通滚动，辅助图层scrub | 普通滚动，短线scrub | 0 |
| S03 把自己放上网页 | 第一个实际作品、需求和方法 | 图形列sticky；在自然文章高度中scrub | 上下布局，视窗边界scrub | 0 |
| S04 移动之前 | 第二项目最关键的预览→确认→执行 | 仅流程示意舞台短pin＋scrub | 三步纵向展开，无pin | 桌面0.60V；手机0 |
| S05 尚未写完 | 计划项目与真实时间线 | 普通滚动，时间线局部scrub | 同左，无额外高度 | 0 |
| S06 下一页 | 邮箱、复制与GitHub | 普通滚动，开口框scrub | 普通滚动，短边界scrub | 0 |

V为当前视口高度的测量基准。桌面额外距离合计1.30V、上限1.50V；这是两个演示所需的预算，不是六场各加一屏。1440×900下建议约1170px额外距离；每个舞台本身的高度仍计算在正常内容中。手机**不加pin占位**，所有演出利用本来就要阅读的距离。实际文章增高时不把字体压小来维持预算。

pin舞台高度最多 `min(0.72V, 680px)`，顶部让出固定导航；不能把超出屏幕高度的正文pin住。宽度≥1100且高度≥720才启用两个pin；平板、横向矮屏和200%缩放后不满足条件时使用普通布局。布局条件在实现后须按真实渲染复核。

## S01 · 先写一版。 / OPEN DRAFT

**目的**：首次进入就知道这是Sakura的学生作品集；滚动后看到“修订”，而非只看到一个好看的标志。文字 C01–C05。

**图层**：L1纸灰背景；L2两层原创字形校样/版面（装饰、aria-hidden）；L3开口框；L4姓名、学校、主题与作品/联系入口。L4从p=0就可读可操作，不随L2缩放或裁切。

| 进度 | 文字与画面状态 | 为什么这样动 |
| --- | --- | --- |
| 进入 / p=0 | “先写一版。”左侧完整；右侧两张相同文字结构的装饰副本错位约24px；框右边有开口；身份与入口可见 | 第一眼先认人和主题，错位是待处理关系，不是假代码 |
| 初期 / 0–0.20 | 背景副本沿同一水平轴靠拢，位移24→8px；框上边拉到正文基线 | 从“多种可能”收向一个决定，只有两个主运动对象 |
| 中段 / 0.20–0.65 | 副本合为一层，开口框由右侧短边变成明确内容视窗；“再认真修改。”作为装饰对应短句沿裁切边展开 | 文案中的“修改”对应看得见的对齐动作；不是打字机逐字等待 |
| 后段 / 0.65–1 | 视窗高度收为下一场页边规则的厚度；标题留足稳定区间后自然上移，解除pin | 完成一次决定，给下一场阅读空间 |
| 结束 | 开口框下边与S02上边界同宽，普通文档流接管 | 接续的是边界关系，不用全屏色块遮住内容 |

向上滚动恢复错位层；姓名/链接不倒放消失。锚点跳到作品时直接离开此场，不强迫完整观看。手机让主标题保持静止；右上装饰副本只移动12px，边框在首屏上半离开到离开视口之间对齐，取消全屏收缩。

## S02 · 我从这里开始。 / STARTING POINT

**目的**：让真实的人与技术方向获得一次静止阅读。文字 C06–C12。此处主动放缓，参考R02的空间层级，而不是复制人物近景。

**进入**：纸灰阅读场域；姓名/学校与介绍左对齐，右侧是三组基础与一组关注方向；S01的框线停在页边。正文全部存在，不按滚动分句隐藏。

**初期 0–0.25**：一条短朱红基线从页边延至“C / C++、Python”的组别标题下方，长度进度与滚动绑定；无百分比能力条。

**中段 0.25–0.70**：标题与段落正常向上经过视口；装饰版框内的三块矩形从松散间距变成统一行距。技术标签本身不飞行、不换位；“正在学习”“关注方向”维持明确区别。

**结束 0.70–1**：基础组下的边界向右转折，成为S03封面视窗的左边；原位置保留细规则，不像内容被搬走。下一场提前出现“能用，再讲为什么。”，接着出现真实项目名。

无pin；默认场景高度由实际介绍和技能内容决定。手机只保留基线长度变化，不叠加多层错位。S02不是一份“技术全部点亮”的能力演出。

## S03 · 把自己放上网页。 / IN USE

**目的**：解释已有作品能做什么，以及为什么这样组织。文字 C13–C23。项目正式名称“个人作品集网站”保留，章节标题不替代其名称。

**进入**：项目索引、筛选、两项已实现/一项计划的状态，以及本项目详情/源码/线上链接先出现。左侧是原创视窗模型（标注“版式示意”，不是伪造旧版本截图），右侧是实际说明。大标题“能用，再讲为什么。”在项目区域只出现一次。

| 进度 | 形与文字 | 层级变化 |
| --- | --- | --- |
| 0–0.20 | 视窗边界沿S02规则展开，内部保留大标题、导航、正文三块平面 | 把抽象框变成可解释的网页结构 |
| 0.20–0.55 | 装饰导航块沿横向分到顶栏，正文块扩至可读宽度；案例正文正常滚动到“清楚的入口” | 从整张封面聚焦一个真实问题：找到内容 |

图形列只在自然文章高度足够时sticky，不增加空白滚动；移动的是其内部装饰，不移动sticky/pin容器本身。手机采用两幅有标签的“宽屏 / 窄屏”示意，边框短程scrub，正文与按钮在其前后正常阅读，不把桌面横向变形硬塞进小屏。

文章固定包含：原生技术选型、移动菜单/筛选/复制、GitHub Pages与资源路径、测试与边界。不把开发内部步骤全部塞进封面。复杂内容继续由详情页承接。

## S04 · 移动之前，先看清楚。 / BEFORE THE MOVE

**目的**：把文件工具最重要的设计决定做成可理解的动态演示。文字 C24–C32。网页不会真的读取或移动文件。

进入项目时，正式名称、Python标签、默认只预览、不覆盖、详情与下载链接先正常呈现；下方才是可pin的**装饰流程舞台**。舞台外有一份普通的三步文本，屏幕阅读器不必依赖演出。

**示意数据**：`sample.txt → documents/sample.txt` 与一个“目标已存在→跳过”示意行，不使用用户实际文件名，不展示真实整理日志。

| 进度 | 构图与动作 | 叙事/事实边界 |
| --- | --- | --- |
| 进入 / 0 | 左侧是原文件项，右侧目标列为空框；标题“先列去向” | 首先说明是预览，文件没有移动 |
| 初期 / 0–0.25 | 目标路径作为同一行的第二列被裁切展开；原文件不移位 | 动画在解释“看清计划”，不是执行 |
| 中前 / 0.25–0.45 | 路径稳定；确认栏出现示意文字“确认后才执行”，留一段保持区 | 滚动不是给工具发送MOVE命令；这是流程模型 |
| 中后 / 0.45–0.80 | 一个装饰文件块沿短路径进入目标列；示意重名行留在原处并标“跳过” | 执行与跳过的差异有明确图形证据 |

上滚时图形回退，但脚本不支持自动撤销：舞台旁明确写“流程示意，不会操作你的文件；工具暂无自动撤销”。不要用“可逆整理”命名场景。

桌面只pin约0.60V滚动距离，舞台最多0.6V高；详细限制位于正常文档流。手机取消pin，将三步排为短纵向带，在0→1的自然滚动中描出连接线、展开列，不让演示盖住下载入口。每步文字自始可读。

## S05 · 还没完成，也写明白。 / STILL OPEN

**目的**：诚实说明下一步，让时间线成为证据而非装饰。文字 C33–C42。

**进入**：C++学生信息管理系统仅有轮廓框、计划状态和具体练习目标；与已实现项目明显分开。“尚未实现”不是低对比小字。

**初期 0–0.25**：开口框下边延伸到计划的第一行，但右上边始终不闭合；计划文本保持可见。

**中段 0.25–0.75**：用户展开原生学习记录时，日期旁的细线按滚动位置延长。只表达当前阅读到哪里，不点亮“掌握”“认证”节点；日期按真实发生事项写。

**结束 0.75–1**：时间线终点保持开口，不出现完成百分比；一句“已经发生的，留下记录；还没做的，写清下一步。”收束。线尾延伸方向与S06邮件地址下划线相同。

无pin、无额外高度、没有强制展开details。未展开时直接进入联系区域；展开/关闭造成高度变化时重新测量后续场景。手机不改变阅读顺序。

## S06 · 下一页，从来信开始。 / WRITE BACK

**目的**：完成主题回扣，也把行动入口交给访问者。文字 C43–C49。

**进入**：邮箱、复制与GitHub已经可见；标题与一个保留开口的矩形组成末页。联系段落不做大面积变色扫过。

**初期 0–0.25**：S05线尾在本场顶部形成版框的一条边；矩形开口朝向邮箱，整体只横移8–16px。

**中段 0.25–0.70**：矩形右边延伸、底边停在邮箱下方，形成“下一页”的可书写空间；标题装饰副本略收窄字距，不改变可读标题本身。

**结束 0.70–1**：版框停止，邮箱、复制反馈、GitHub维持稳态。页面最后保持空白，不做黑场、不把联系方式卷走、不强制回顶。

无pin、无额外滚动；手机只动画下划线，不缩放整块联系内容。滚到文档末尾时即使视口较高、自然范围不足，也直接显示完备联系状态，不要求用户“再滚一屏”。

## 连续性检查：每次继承什么

| 场景接口 | 继承物 | 改变什么 | 保持什么 |
| --- | --- | --- | --- |
| S01→S02 | 开口版框的一条水平边 | 展示态→阅读态 | 同一基线与边距 |
| S02→S03 | 页边规则 | 单线→项目窗口 | 左对齐坐标 |
| S03→S04 | 窗口下边 | 网页内容列→文件去向列 | 矩形与列关系 |
| S04→S05 | 结果记录的末行 | 已执行示意→未实现计划 | 真实状态文字的优先级 |
| S05→S06 | 开放线尾 | 时间线→邮件下划线 | 未闭合意味着还可继续 |

这些graphic match通过相邻场景共享边距/尺寸、交接区间的两份装饰副本完成，不必让一个fixed巨型对象跨越整站。副本交接只交给装饰；实际标题、文本和可操作元素始终各自在DOM中，不做跨章DOM搬移。

## 响应式、降级与实际操作

- **减少动态效果**：移除全部pin占位、scrub、尺度变化和层叠位移；显示每场清楚的静态构图。不能只是把动画时长设为0，却留着长空白。
- **无JS/脚本加载失败**：普通文档流包含完整身份、项目、技能、学习记录和联系。没有为了动画而默认opacity:0的正文。
- **键盘**：Tab不被困在pin区；焦点滚入按钮时不重置页面位置。装饰副本aria-hidden，不复制链接或可聚焦元素。详情页返回定位到项目标题。
- **锚点/刷新**：导航直接到实际语义section；深链接刷新时初始化到当前p，而不是先播首屏。分享`#contact`不能先从首页演出开始。
- **筛选**：保留现有按技术筛选行为。隐藏项目时须连同其场景容器、占位与时间轴一起撤销，完成DOM变化后重建/refresh可见场景。直接跳转被筛掉的项目需先恢复对应可见状态，禁止残留空pin。
- **详情展开、窗口变化、字体就绪**：统一重新测量，不在每个scroll事件中重新算所有布局。导航、筛选、details都不需要等待动画完成。
- **滚轮控制**：不preventDefault，不接管触摸惯性，不引入平滑滚动库、ScrollSmoother、normalizeScroll或滚动吸附。

## 实现路线比较与推荐

| 路线 | 适合的任务 | 限制与决定 |
| --- | --- | --- |
| CSS scroll()/view() | 单一框线、颜色、短形状随视口变化 | 用@supports检测；复杂跨层时间轴和pin协调要另处理；未实测前不宣称全浏览器一致 |
| 原生JS＋WAAPI/单次rAF写入 | 少数场景、严格零运行依赖 | 需自行处理测量缓存、反向、回收、resize、锚点和分段映射；不是把IntersectionObserver换个名字 |
| GSAP core＋ScrollTrigger | 两处pin与多个分段scrub统一编排 | 增加本地运行资源与维护；下一轮先做一个验证样片，核对具体版本、许可、体积和目标浏览器 |

**建议下一轮以GSAP＋ScrollTrigger做小样，再决定是否采用。** 本轮没有安装依赖、引入库或写动画代码。若采用，固定版本、自托管至相对资源路径、保留许可，不依赖CDN；不叠加第二套库控制同一属性。使用现代 [gsap.matchMedia](https://gsap.com/docs/v3/GSAP/gsap.matchMedia()/) 分别创建/撤销桌面、手机与减少动态效果场景；旧ScrollTrigger.matchMedia不作新代码入口。pin容器不参与自身变形，移动内部层。CSS原生方案的概念见 [MDN指南](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll-driven_animations/)。

这些是方案取舍，非已证明的性能结论。下一轮验收至少在0/25/50/75/100%及反向采样，检查同一滚动位置得到同一状态；两张静态首屏截图不能证明scroll-driven实现成立。
